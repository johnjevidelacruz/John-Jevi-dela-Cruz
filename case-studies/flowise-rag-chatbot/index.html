Separating chatbot ingestion from the public runtime

Reworking a retrieval-augmented chatbot so the public embed used only the runtime path and no longer triggered an ingestion-related error.

Case studyContextProblemMy roleChangeResult

Context

The situation

A Flowise chatbot using retrieval-augmented generation over an Excel dataset.

Problem

What was getting in the way

The public embed returned a 400 error because ingestion and credential-dependent nodes were included in the runtime flow.

My role

My role in the work

  • Flow architecture
  • Dataset ingestion and retrieval configuration
  • Runtime/embed troubleshooting
  • Deployment through GitHub Pages

What I found

The underlying issue

The error was isolated to nodes needed to load and index data, not to the public question-and-answer runtime itself.

What I changed

What I changed

  • Separated ingestion and credential nodes from the public runtime flow
  • Configured Qdrant retrieval and Jina embeddings
  • Used GroqChat with a conversational retrieval QA chain
  • Removed source-document chips from the public widget

What stayed in place

What the team could keep using

A clear boundary between controlled ingestion and the public runtime.

Systems used

Flowise, GroqChat, Qdrant Vector Store and Retriever, Jina Embeddings v3, Excel/File Loader and Character Text Splitter.

Outcome

The result

The architecture change and deployment are documented. No unsupported user-adoption, accuracy or production-scale claim is made.

Practical benefit

The public widget can run against the prepared knowledge base without exposing ingestion steps or credentials.
