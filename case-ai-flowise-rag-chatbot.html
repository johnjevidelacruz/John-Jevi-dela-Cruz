Case study

Flowise RAG Chatbot: Ops/Contacts Knowledge Base with Qdrant + Jina Embeddings

The goal was a simple internal knowledge bot: ask a question, get a grounded answer from company data. The challenge was making it reliable in Flowise while keeping the public embed safe and stable.

← Back to case studies

At a glance

  • Role: Builder / automation specialist
  • Stack: Flowise, Qdrant Cloud, Jina Embeddings v3, GroqChat
  • Deliverables: Ingestion flow, runtime flow, embed-safe deployment, documentation

Key highlights

  • Split ingestion vs runtime for embed safety
  • Qdrant-based RAG with Jina embeddings
  • Resolved 400 embed errors by removing ingestion nodes

Context

Built a Flowise website chatbot using GroqChat + RAG over an Excel employee/contacts dataset, with Qdrant as the vector database.

Objective

Deliver a chatbot that works reliably in both the Flowise canvas and an embedded website widget—without exposing internal source chunks.

Constraints

Flowise version lacked certain upsert/retriever nodes, and embed initially failed due to ingestion/credential nodes being present in the public flow.

Approach

I separated ingestion from runtime and used Qdrant nodes for write and read paths.

  • Ingestion flow: splitter → Excel/File loader → Qdrant Vector Store (write) + Jina embeddings.
  • Runtime flow: Qdrant Retriever → Conversational Retrieval QA Chain + GroqChat.
  • Created a runtime-only chatflow for embedding to avoid 400 errors from credential nodes.
  • Disabled returnSourceDocuments/showSourceDocument to hide internal chunks in the widget.

Deliverables

A working RAG architecture with documented wiring and prerequisites.

  • Qdrant Cloud collection configured (1024-dim embeddings).
  • Working canvas flow + separate embed-safe runtime flow.
  • Wiring notes for Flowise port-to-port constraints.
  • Deployment via Flowise-embed JS snippet on GitHub Pages.

Results

Chatbot runs correctly in canvas and embed. Ingestion can be run privately without breaking the public-facing runtime flow.

Reusable checklist

If you’re doing something similar, this is the short checklist I follow to keep the work clean and close-ready.

  • Separate ingestion/build from runtime/serve for anything that will be embedded publicly.
  • Treat vector DB as system of record: consistent embedding dims and stable collection naming.
  • Hide source docs in customer-facing widgets unless your use-case requires transparency.
  • Document wiring constraints so future edits don’t break connections.
